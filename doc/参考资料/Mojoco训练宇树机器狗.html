1. 项目概述：在MuJoCo中运行宇树Go2机器狗

如果你正在研究四足机器人，尤其是宇树科技的Go2机器狗，并且希望在一个高保真的物理仿真环境中测试你的控制算法，那么将Go2部署到MuJoCo仿真器中是一个必经之路。这不仅仅是让一个3D模型动起来那么简单，它关乎如何打通从仿真到实物的“最后一公里”，让你在电脑上编写的代码，能够无缝对接到真实的机器人硬件上。宇树官方提供的 unitree_mujoco 项目，正是为此而生的一套桥梁工具。

简单来说，这个项目允许你使用与真实Go2机器狗完全相同的底层通信接口（基于Unitree SDK2），在MuJoCo中驱动一个高精度的动力学模型。这意味着，你为仿真环境开发的站立、行走、小跑等控制程序，只需修改一行网络配置，就能直接发送给实验室或场地里的实体Go2执行。对于机器人开发者、高校研究团队以及算法工程师而言，这极大地降低了开发成本与风险，你可以在仿真中无限次地、安全地“摔打”你的算法，直到它足够稳健，再放到昂贵的实体机器人上验证。

整个流程涉及几个核心环节：搭建MuJoCo仿真环境、编译安装宇树的SDK与仿真桥接包、配置机器人模型与场景，最后通过C++、Python或ROS2接口发送控制指令。虽然官方README提供了基础步骤，但在实际部署中，从系统依赖、版本兼容到网络配置，每一步都可能藏着需要你亲自趟过去的“坑”。接下来，我将结合多次部署的经验，为你拆解从零开始到让Go2在MuJoCo中活起来的完整过程，并分享那些文档里不会写的实操细节和避坑指南。

2. 环境准备与核心依赖解析

要让Go2在MuJoCo里跑起来，你得先搭好台子。这个“台子”由三块基石构成：MuJoCo物理引擎本体、宇树机器人的官方SDK2、以及连接二者的 unitree_mujoco 桥接包。选择正确的版本和安装路径，是避免后续一系列编译错误的关键。

2.1 MuJoCo 3.3.0+ 安装详解

MuJoCo作为仿真核心，其安装主要分为两步：获取许可证（自2021年10月被DeepMind收购并开源后，已完全免费）和放置库文件。

第一步：下载与解压 访问MuJoCo官网，下载最新稳定版本（例如 mujoco-3.3.0-linux-x86_64.tar.gz）。我强烈建议使用3.3.0或更高版本，以确保对最新API的兼容性。下载后，执行以下操作：

  1. # 创建MuJoCo的标准配置目录
  2. mkdir -p ~/.mujoco
  3. # 将压缩包解压至该目录，并重命名为一个简单的路径（方便后续链接）
  4. tar -xzf mujoco-3.3.0-linux-x86_64.tar.gz -C ~/.mujoco/

此时，你的 ~/.mujoco 目录下应该有一个名为 mujoco-3.3.0 的文件夹。里面包含运行所需的 bin, lib, include 等子目录。

第二步：设置环境变量 为了让系统和其他软件能找到MuJoCo，需要将它的库路径加入环境变量。编辑你的 ~/.bashrc 文件（如果你使用zsh，则是 ~/.zshrc）：

  1. export MUJOCO_PATH="$HOME/.mujoco/mujoco-3.3.0"
  2. export LD_LIBRARY_PATH=$LD_LIBRARY_PATH:$MUJOCO_PATH/bin
  3. export MJLIB_PATH=$MUJOCO_PATH/lib/libmujoco.so

保存后，执行 source ~/.bashrc 使配置生效。你可以通过运行 $MUJOCO_PATH/bin/simulate 来测试基础仿真器是否能够正常启动一个空白场景。

注意：很多教程会建议将解压后的文件夹直接命名为 mujoco，但为了便于管理多个版本，我建议保留版本号。在后续链接时，我们可以通过软链接来创建一个无版本号的路径指向它。

2.2 Unitree SDK2 安装与路径规划

宇树SDK2是控制真实机器人的通信中间件，仿真桥接包需要调用它的头文件和库。官方推荐将其安装到 /opt/unitree_robotics 目录，这是一个好习惯，可以保持系统目录的整洁，并方便多用户访问。

安装步骤：

  1. # 1. 克隆仓库
  2. git clone https://github.com/unitreerobotics/unitree_sdk2.git
  3. cd unitree_sdk2
  5. # 2. 创建构建目录并指定安装前缀
  6. mkdir build && cd build
  7. cmake .. -DCMAKE_INSTALL_PREFIX=/opt/unitree_robotics
  9. # 3. 编译并安装
  10. make -j$(nproc)  # 使用所有CPU核心加速编译
  11. sudo make install  # 需要sudo权限写入/opt目录

安装完成后，检查 /opt/unitree_robotics 目录，你应该能看到 include、 lib、 share 等子目录。unitree_mujoco 在编译时会自动到这个路径下寻找依赖。

为什么强调安装路径？ 因为 unitree_mujoco 的CMakeLists.txt中，默认通过 find_package(unitree_sdk2 REQUIRED) 来查找SDK。而SDK的安装包配置文件（unitree_sdk2Config.cmake）会安装在 /opt/unitree_robotics/lib/cmake/ 下。如果你安装到其他路径，就需要通过 -Dunitree_sdk2_DIR=/your/custom/path/lib/cmake 手动指定给CMake，这对新手来说容易出错。

2.3 系统级依赖安装

在编译 unitree_mujoco 之前，还需要安装一些系统库。这些库提供了YAML解析、日志、图形界面等基础功能。

  1. sudo apt update
  2. sudo apt install -y libyaml-cpp-dev libspdlog-dev libboost-all-dev libglfw3-dev
  • libyaml-cpp-dev: 用于解析仿真器的YAML配置文件。
  • libspdlog-dev: 一个快速的C++日志库，仿真器用它来输出运行状态和调试信息。
  • libboost-all-dev: 提供了线程、时间、程序选项等C++扩展功能，SDK中广泛使用。
  • libglfw3-dev: MuJoCo仿真可视化窗口所依赖的OpenGL上下文和窗口管理库。

确保你的系统是Ubuntu 20.04或22.04，这是经过充分测试的环境。其他发行版可能需要从源码编译这些依赖，复杂度会陡增。

3. 编译与运行 unitree_mujoco 仿真器

环境就绪后，现在进入核心环节——编译桥接仿真器。unitree_mujoco 仓库提供了C++和Python两个版本的仿真器。C++版本性能更高，更接近真实控制循环的时序，是进行严肃控制算法开发的推荐选择。Python版本则更适合快速原型验证和脚本化测试。

3.1 C++ 仿真器编译实战

第一步：克隆仓库与创建软链接

  1. git clone https://github.com/unitreerobotics/unitree_mujoco.git
  2. cd unitree_mujoco/simulate
  3. # 创建指向MuJoCo目录的软链接，命名为“mujoco”。这是编译脚本的硬性要求。
  4. ln -sfn ~/.mujoco/mujoco-3.3.0 ./mujoco

这个软链接操作至关重要。项目中的CMakeLists.txt会直接寻找当前目录下的 mujoco 文件夹来定位头文件和库。如果链接失败，编译时会报错找不到 mujoco.h。

第二步：CMake配置与编译

  1. mkdir build && cd build
  2. cmake .. -DCMAKE_BUILD_TYPE=RelWithDebInfo
  3. make -j$(nproc)

如果一切顺利，你会在 build 目录下看到生成的可执行文件 unitree_mujoco 和测试程序 test。

第三步：首次运行与问题排查 尝试运行仿真器加载Go2模型：

  1. ./unitree_mujoco -r go2 -s scene_terrain.xml
  • -r go2: 指定机器人型号为Go2。
  • -s scene_terrain.xml: 指定场景文件为带地形的版本。

常见问题1：GLFW初始化失败 如果提示 GLFW initialization failed，很可能是因为你正在通过SSH连接服务器，而没有图形界面转发。你需要确保SSH连接时加了 -X 或 -Y 参数启用X11转发，并且服务器上安装了 xorg 相关包。对于无头服务器，可以考虑使用 MUJOCO_GL=osmesa 环境变量切换到软件渲染（但性能较差），或者使用虚拟帧缓冲器 xvfb。

常见问题2：无法找到共享库 如果提示 error while loading shared libraries: libmujoco.so.3.3.0: cannot open shared object file，说明系统运行时库路径未包含MuJoCo。即使你在 .bashrc 中设置了 LD_LIBRARY_PATH，但某些启动方式（如系统服务或某些IDE）可能不会继承用户环境变量。一个更稳妥的方法是将MuJoCo库路径添加到系统配置中：

  1. sudo echo "$HOME/.mujoco/mujoco-3.3.0/bin" > /etc/ld.so.conf.d/mujoco.conf
  2. sudo ldconfig

3.2 Python 仿真器环境搭建

Python版本更适合交互式开发和集成到机器学习管道中（如配合Gymnasium环境）。

第一步：安装Python依赖

  1. cd ~
  2. # 安装宇树Python SDK
  3. git clone https://github.com/unitreerobotics/unitree_sdk2_python.git
  4. cd unitree_sdk2_python
  5. pip3 install -e .  # 以可编辑模式安装，方便修改代码
  7. # 安装MuJoCo Python绑定和游戏手柄支持库
  8. pip3 install mujoco pygame

注意一个关键坑点：unitree_sdk2_python 依赖 cyclonedds 作为DDS中间件。如果安装过程中报错 Could not locate cyclonedds，你需要手动安装它：

  1. sudo apt install -y ros-humble-rmw-cyclonedds-cpp  # 对于Ubuntu 22.04和ROS2 Humble
  2. # 或者从源码安装
  3. git clone https://github.com/eclipse-cyclonedds/cyclonedds.git
  4. cd cyclonedds
  5. mkdir build && cd build
  6. cmake .. -DCMAKE_INSTALL_PREFIX=/usr/local
  7. make -j$(nproc)
  8. sudo make install

安装后，可能需要设置环境变量 export CYCLONEDDS_HOME=/usr/local。

第二步：运行Python仿真器

  1. cd unitree_mujoco/simulate_python
  2. python3 ./unitree_mujoco.py

同样，你需要确保有图形界面。运行后，应该能看到与C++版本相同的仿真界面。

4. 仿真器配置与核心功能解析

成功启动仿真器只是第一步，如何配置它以满足你的开发需求，才是重点。unitree_mujoco 通过配置文件来管理机器人型号、通信、输入设备等关键参数。

4.1 配置文件深度解读

C++版本配置 (simulate/config.yaml)：

  1. robot: "go2"                # 加载的机器人型号，可选 "go2", "b2", "b2w", "h1"
  2. robot_scene: "scene.xml"    # 场景文件，对应 unitree_robots/[robot]/ 下的文件
  3. domain_id: 1                # DDS域ID，仿真与实物区分的关键！
  4. use_joystick: 1             # 是否启用游戏手柄模拟遥控器
  5. joystick_type: "xbox"       # 手柄类型，"xbox" 或 "switch"
  6. joystick_device: "/dev/input/js0" # 手柄设备文件
  7. interface: "lo"             # 网络接口，仿真时推荐本地回环"lo"
  8. print_scene_information: 1  # 是否打印模型关节、传感器信息，调试时非常有用
  9. enable_elastic_band: 0      # 是否启用虚拟弹力带（针对H1双足机器人）

Python版本配置 (simulate_python/config.py)： 参数与C++版基本对应，但以Python变量的形式存在。注意 JOYSTICK_DEVICE 在Python中通常是设备编号（如0, 1），而非设备路径。

domain_id 与 interface 的黄金法则： 这是实现“仿真-实物”一键切换的核心。

  • 仿真模式：设置 domain_id=1 (或任意非0值)，interface="lo"。这样仿真器内部通过本地回环网络通信，与外部物理网络隔离。
  • 实物模式：当你连接真实Go2时，需要将控制程序的 domain_id 改为 0（Go2默认域ID），并将 interface 设置为连接机器人的物理网卡名（如 enp3s0, eth0）。 通过命令行参数或条件判断来切换这两组配置，你就可以用同一份代码控制仿真模型和真实机器人。

4.2 游戏手柄集成与遥控器模拟

仿真器内置了将普通游戏手柄映射为宇树无线遥控器的功能。这对于测试机器人的运动指令非常方便。

配置与测试手柄：

  1. 将你的Xbox或Switch手柄通过USB连接到电脑。
  2. 使用 jstest /dev/input/js0 命令测试手柄是否被识别，并查看各个按钮和摇杆的编号。
  3. 在配置文件中设置 use_joystick: 1 和正确的 joystick_type。

键位映射原理： 仿真器源码中（如 simulate/src/unitree_sdk2_bridge/unitree_sdk2_bridge.cc）硬编码了映射关系。例如，Xbox手柄的左侧摇杆（LX, LY）通常被映射为控制机器人前进、后退和旋转的速度指令。如果你使用非标准手柄，可能需要根据 jstest 的输出，手动修改源码中的 axis_id 和 button_id 映射字典，然后重新编译。

一个实用技巧：你可以通过运行测试程序 ./test (C++) 或 python3 ./test/test_unitree_sdk2.py (Python)，并在另一个终端运行仿真器，来观察手柄输入如何转化为电机扭矩指令。测试程序会持续发送1Nm的扭矩，结合手柄控制，你可以直观地看到机器人关节的运动。

4.3 地形工具与场景构建

除了平地，你肯定希望机器人在更复杂的地形上测试。terrain_tool 目录下提供了地形生成工具。

  1. cd unitree_mujoco/terrain_tool
  2. mkdir build && cd build
  3. cmake .. && make
  4. ./terrain_tool

运行后，它会生成一个 terrain.xml 文件。你可以通过修改源码中的参数（如台阶高度、粗糙度网格大小）来创建楼梯、崎岖路面或高度场。然后，在仿真器启动时，通过 -s 参数指定这个自定义的地形文件，或者将其内容合并到 unitree_robots/go2/scene_terrain.xml 中。

自定义场景进阶： MuJoCo的场景文件是XML格式的，你可以直接编辑它们。例如，在 scene.xml 中，你可以：

  • 添加障碍物（<geom type="box" ... />）。
  • 改变地面摩擦力（<geom ... friction="1.0 0.005 0.0001" />）。
  • 调整重力方向或大小（<option gravity="0 0 -9.81" />）。
  • 添加额外的传感器，如力传感器、陀螺仪等。 这为你的算法提供了无限的测试场景可能性。

5. 从仿真到实物：代码移植实战

仿真的终极目标是服务于实物。unitree_mujoco 最大的优势在于，它使用了与真实机器人完全相同的 unitree_sdk2 通信接口。让我们通过一个“站立-趴下”的示例，来剖析如何编写一份同时兼容仿真和实物的控制代码。

5.1 基于C++ SDK2的示例剖析

查看 example/cpp/stand_go2.cpp，其核心逻辑如下：

  1. int main(int argc, char *argv[]) {
  2.     // 关键：根据输入参数判断是仿真模式还是实物模式
  3.     if (argc < 2) {
  4.         // 无参数，仿真模式：使用域ID=1和本地回环
  5.         ChannelFactory::Instance()->Init(1, "lo");
  6.         std::cout << "Simulation Mode (Domain ID=1, interface=lo)" << std::endl;
  7.     } else {
  8.         // 有参数（网卡名），实物模式：使用域ID=0和指定网卡
  9.         ChannelFactory::Instance()->Init(0, argv[1]);
  10.         std::cout << "Real Robot Mode (Domain ID=0, interface=" << argv[1] << ")" << std::endl;
  11.     }
  13.     // 创建LowLevel类型的通信通道，用于发送低级控制指令
  14.     auto channel = ChannelFactory::Instance()->CreatePubChannel<LowCmd>("rt/lowcmd");
  15.     auto cmd = std::make_shared<LowCmd>();
  17.     // 1. 站立：设置所有关节为位置模式，并给定一个初始站立角度
  18.     std::cout << "Standing up..." << std::endl;
  19.     for (int i = 0; i < 12; ++i) { // Go2有12个关节（每条腿3个）
  20.         cmd->motorCmd[i].mode = MotorMode::POSITION;
  21.         cmd->motorCmd[i].q = stand_joint_angles[i]; // 预定义的站立角度数组
  22.         cmd->motorCmd[i].Kp = 100.0; // 位置环刚度
  23.         cmd->motorCmd[i].Kd = 3.0;   // 位置环阻尼
  24.     }
  25.     for (int t = 0; t < 500; ++t) { // 持续发送500个控制周期（约1.5秒）
  26.         channel->Write(cmd);
  27.         usleep(3000); // 模拟3ms的控制周期
  28.     }
  30.     // 2. 趴下：将关节角度设置为趴下的姿势
  31.     std::cout << "Lying down..." << std::endl;
  32.     for (int i = 0; i < 12; ++i) {
  33.         cmd->motorCmd[i].q = lie_down_joint_angles[i];
  34.     }
  35.     for (int t = 0; t < 500; ++t) {
  36.         channel->Write(cmd);
  37.         usleep(3000);
  38.     }
  39. }

编译与运行：

  1. cd example/cpp
  2. mkdir build && cd build
  3. cmake .. && make
  4. # 仿真运行
  5. ./stand_go2
  6. # 连接真实Go2运行（假设网卡名为enp3s0）
  7. ./stand_go2 enp3s0

5.2 基于ROS2的集成开发

对于更复杂的系统，ROS2是机器人开发的事实标准。宇树提供了 unitree_ros2 包。仿真环境下的ROS2配置需要一点技巧。

环境配置：

  1. # 假设unitree_ros2已安装在~/unitree_ros2
  2. # 对于仿真，source一个使用本地回环的setup文件
  3. source ~/unitree_ros2/setup_local.sh
  4. # 设置ROS_DOMAIN_ID与仿真器config.yaml中的domain_id一致
  5. export ROS_DOMAIN_ID=1

setup_local.sh 脚本内部通常设置了 ROS_LOCALHOST_ONLY=1，强制ROS2使用本地回环，避免仿真数据干扰同一网络下的其他ROS2节点。

编译与运行示例：

  1. cd example/ros2
  2. colcon build --packages-select stand_go2
  3. source install/setup.bash
  4. ros2 run stand_go2 stand_go2

在ROS2节点中，你通过 rclcpp 创建Publisher来发布 unitree_ros2_msg::msg::LowCmd 消息，其数据类型与SDK2中的 LowCmd 是完全对齐的。这意味着，你的算法核心可以写成独立的C++类或Python函数，然后分别包装成一个ROS2节点和一个直接调用SDK2的应用程序，两者共享同一份算法逻辑。

5.3 仿真-实物切换的工程化实践

在实际项目中，我推荐采用以下模式来管理配置，而不是在代码中写死 if-else：

1. 使用配置文件或环境变量：

  1. // 从环境变量读取模式
  2. const char* env_mode = std::getenv("ROBOT_MODE");
  3. bool is_simulation = (env_mode != nullptr && std::string(env_mode) == "simulation");
  5. int domain_id = is_simulation ? 1 : 0;
  6. std::string interface = is_simulation ? "lo" : "enp3s0";
  7. ChannelFactory::Instance()->Init(domain_id, interface);

运行前，通过 export ROBOT_MODE=simulation 来切换。

2. 使用参数解析库（如Boost.Program_options）： 这样可以通过统一的命令行接口来指定模式、域ID、网卡等，更加灵活。

3. 在ROS2中使用节点参数：

  1. // 在ROS2节点中声明参数
  2. this->declare_parameter("simulation", true);
  3. this->declare_parameter("domain_id", 1);
  4. this->declare_parameter("interface", std::string("lo"));
  6. bool sim = this->get_parameter("simulation").as_bool();
  7. int domain = this->get_parameter("domain_id").as_int();
  8. std::string iface = this->get_parameter("interface").as_string();
  9. // 然后根据参数初始化SDK2通道

这样可以通过启动文件或命令行动态覆盖参数。

6. 高级调试与性能优化技巧

当你的仿真环境跑通后，接下来就要追求稳定性和效率了。这里分享几个从实际项目中积累的调试和优化经验。

6.1 仿真同步与实时性保证

MuJoCo仿真默认以尽可能快的速度运行。但对于机器人控制，我们需要严格的实时性，即仿真时间步长必须与控制周期匹配。在 simulate_python/config.py 中，有两个关键参数：

  • SIMULATE_DT: 仿真物理步长，默认0.003秒（3ms）。这决定了动力学计算的精度和速度。
  • VIEWER_DT: 可视化更新步长，默认0.02秒（50Hz）。这决定了你看到画面的流畅度。

如何设置合理的步长？

  • SIMULATE_DT 应等于或略小于你的控制周期。例如，Go2的真实控制周期是2ms或3ms。如果仿真步长设为5ms，可能会因计算过于“粗糙”而引入数值不稳定，导致机器人抖动甚至摔倒。
  • VIEWER_DT 可以比 SIMULATE_DT 大，因为渲染是耗时的。但如果你需要实时观察高频数据（如关节力矩波形），可以适当调小，代价是更高的CPU占用。

在C++仿真器中，步长通常在源码的 simulate/src/unitree_mujoco/unitree_mujoco.cc 中的主循环里通过 mj_step 函数和 std::chrono 延时来控制。你需要确保循环耗时稳定在设定的步长时间附近，否则仿真会变快或变慢。

6.2 传感器数据验证与噪声注入

仿真器提供的传感器数据（关节编码器、IMU）是完美的，没有噪声和延迟。但真实世界并非如此。为了让仿真更贴近现实，你需要主动在算法中引入噪声和延迟模型，或者在仿真端进行修改。

方法一：在控制算法中处理 在读取仿真器发布的 LowState 消息后，加入高斯白噪声和一步延迟：

  1. // 伪代码
  2. double add_gaussian_noise(double value, double stddev) {
  3.     static std::default_random_engine generator;
  4.     static std::normal_distribution<double> distribution(0.0, stddev);
  5.     return value + distribution(generator);
  6. }
  8. // 在回调函数中
  9. current_angle = add_gaussian_noise(real_angle, 0.001); // 加入0.001弧度的噪声
  10. // 将current_angle放入一个长度为N的缓冲区，取第N-1个值作为带延迟的观测值

方法二：修改仿真器桥接代码（进阶） 你可以修改 unitree_sdk2_bridge.cc 中发布 LowState 消息的部分，在数据发布前对其添加噪声。这样，你的控制算法无需修改，就能接收到带噪声的“更真实”的数据。

6.3 性能瓶颈分析与优化

当仿真变慢或控制周期无法维持时，需要排查瓶颈。

1. 可视化是性能杀手 MuJoCo的渲染非常消耗资源。在无头服务器上训练强化学习模型时，务必关闭可视化。在C++仿真器中，可以注释掉或通过条件编译关闭 mjv_updateScene 和 mjr_render 相关的代码。在Python中，创建 MjSim 对象时不传入 viewer 参数。

2. 使用更简单的模型 unitree_robots/go2 目录下的模型文件可能包含高精度的网格文件用于渲染。你可以创建一个简化版的模型文件，用基本的几何体（如圆柱、立方体）代替复杂的视觉网格，这能大幅提升动力学计算速度。

3. 调整MuJoCo的求解器参数 在MJCF模型文件的 <option> 标签中，可以设置：

  • integrator: 积分器类型。RK4 精度高但慢，Euler 快但精度低。对于四足机器人，通常 RK4 更稳定。
  • iterations: 约束求解器的迭代次数。增加迭代次数可以提高稳定性（尤其接触多时），但会降低速度。默认是100，对于平地行走，可以尝试降低到50看看是否仍稳定。
  • solver: 求解器类型。PGS (投影高斯-赛德尔) 速度快，CG (共轭梯度) 更精确但慢。对于有大量接触的场景，PGS 通常是更好的选择。

4. 检查你的控制算法 有时性能瓶颈不在仿真，而在你自己的控制代码。使用性能分析工具（如 gprof 对C++程序，cProfile 对Python程序）来定位热点函数。确保你的控制循环中没有耗时的文件IO、不必要的内存拷贝或复杂的动态内存分配。

7. 常见问题排查与解决实录

即使按照指南操作，你也难免会遇到各种问题。这里汇总了我和社区中遇到的一些典型问题及其解决方案。

7.1 编译与链接问题

问题：编译 unitree_mujoco 时，报错 fatal error: mujoco.h: No such file or directory

  • 原因：simulate 目录下的 mujoco 软链接不存在或指向错误。
  • 解决：确保在 unitree_mujoco/simulate/ 目录下执行了 ln -sfn ~/.mujoco/mujoco-3.3.0 ./mujoco。使用 ls -la mujoco 检查链接是否有效。

问题：编译时找不到 libunitree_sdk2.so

  • 原因：unitree_sdk2 未安装或安装路径不在CMake的搜索路径中。
  • 解决：
    1. 确认已按照步骤将SDK2安装到 /opt/unitree_robotics。
    2. 尝试手动指定路径：cmake .. -Dunitree_sdk2_DIR=/opt/unitree_robotics/lib/cmake。
    3. 检查 /opt/unitree_robotics/lib 下是否存在 libunitree_sdk2.so 文件。

7.2 运行时问题

问题：运行 ./unitree_mujoco 后，窗口一闪而过，或提示 GLFW error 65543: GLX: Failed to create context

  • 原因：通常是OpenGL上下文创建失败，常见于通过SSH连接的远程服务器或无独立显卡的机器。
  • 解决：
    • 方案A（推荐，用于远程可视化）：确保SSH连接使用了 -X 或 -Y 选项，并且本地和服务器都安装了必要的X11转发组件。在服务器上安装 mesa-utils：sudo apt install mesa-utils。
    • 方案B（用于无头服务器训练）：使用离屏渲染。在运行前设置环境变量：export MUJOCO_GL=osmesa。然后再次运行程序。注意，这需要安装 libosmesa6-dev：sudo apt install libosmesa6-dev。

问题：Python仿真器运行时提示 ModuleNotFoundError: No module named 'unitree_sdk2_python'

  • 原因：Python环境问题。你可能在多个Python环境（如系统Python、conda环境、虚拟环境）中切换。
  • 解决：
    1. 确认你当前使用的Python解释器：which python3。
    2. 确认 unitree_sdk2_python 安装到了这个解释器对应的site-packages中。可以进入Python交互环境，执行 import unitree_sdk2_python 测试。
    3. 如果你使用虚拟环境，请确保在虚拟环境中重新执行 pip3 install -e .。

问题：手柄连接了，但仿真器里的机器人没反应

  • 原因：手柄设备号不对或映射错误。
  • 解决：
    1. 使用 ls /dev/input/js* 查看所有手柄设备。可能是 js0, js1 等。
    2. 修改 config.yaml 中的 joystick_device 为正确的设备号。
    3. 使用 jstest /dev/input/js0 测试手柄，按下按钮看输出是否有变化。确保手柄本身是好的。
    4. 检查 joystick_type 是否与你的手柄类型匹配。如果不匹配，需要按照前面提到的方法修改源码中的映射表。

7.3 通信与网络问题

问题：控制程序（如 stand_go2）运行后，仿真器中的机器人不动，程序也没有报错

  • 原因：DDS域ID不匹配。控制程序和仿真器必须在同一个DDS域内才能通信。
  • 解决：
    1. 检查仿真器 config.yaml 中的 domain_id（例如是1）。
    2. 检查你的控制程序初始化时，是否将 ChannelFactory 的域ID也设为了相同的值（例如1）。如果控制程序是从实物控制代码改过来的，很可能默认是0。
    3. 检查网络接口 interface 是否一致。仿真时两者都应设为 "lo"。

问题：连接真实机器人时，控制程序发送指令，但机器人无响应

  • 原因：多种可能。
  • 排查步骤：
    1. 网络连通性：ping 一下机器人的IP地址（通常是192.168.123.161）。确保电脑和机器人在同一网段，且防火墙没有屏蔽相关端口。
    2. 域ID：真实Go2的默认域ID是0。确保控制程序初始化时 domain_id=0。
    3. 网卡名称：确保 interface 参数设置的是连接机器人的物理网卡名（如 enp3s0），可以通过 ifconfig 或 ip addr 命令查看。
    4. 机器人模式：确保机器人已开机，并进入了 无线手柄待连接状态（橙色灯慢闪）。如果机器人处于其他模式（如内置运动模式），可能不会响应外部SDK的低级指令。
    5. 安全开关：Go2背部的安全开关是否已按下？如果没有按下，电机处于锁死状态。

7.4 模型与动力学问题

问题：仿真中的机器人站立不稳，轻微扰动就摔倒，而真实机器人很稳

  • 原因：仿真模型参数（质量、惯性、摩擦、阻尼）与实物存在差异，或者仿真步长 SIMULATE_DT 设置得太大。
  • 解决：
    1. 调参：仔细核对 unitree_robots/go2/go2.xml 中的动力学参数。你可以尝试微调关节阻尼（<joint damping="...">）和接触摩擦参数。
    2. 减小步长：尝试将 SIMULATE_DT 从0.003减小到0.001或0.002，提高仿真精度。
    3. 检查控制器：你的控制算法可能对模型误差过于敏感。考虑在控制器中增加鲁棒性，例如提高PD控制中的微分增益 Kd，或加入低通滤波来平滑状态反馈。

问题：机器人与地面接触时发生剧烈抖动或穿透

  • 原因：MuJoCo的接触参数设置不当。
  • 解决：在模型文件的 <option> 标签或 <default> 标签中调整接触参数： 
    1. <option>
    2.   <flag contact="enable"/> 
    3.   <flag elasticity="disable"/>
    4.   <flag override="disable"/>
    5. </option>
    6. <default>
    7.   <geom solimp="0.9 0.95 0.001" solref="0.02 1"/> <!-- 调整接触阻抗参数 -->
    8.   <geom friction="1 0.005 0.0001"/> <!-- 滑动、扭转、滚动摩擦 -->
    9. </default>
    • solimp 和 solref 参数非常关键，它们定义了接触的“软硬度”。可以查阅MuJoCo官方文档了解如何调整。
    • 也可以尝试启用 <flag elasticity="enable"/> 来模拟接触弹性，有时能缓解抖动。

将Go2成功运行在MuJoCo中，只是开启了四足机器人算法开发的大门。这个仿真环境的价值，在于它提供了一个安全、可重复、可加速的测试平台。你可以在这里大胆尝试各种激进的控制策略、进行百万次级的强化学习训练、或者模拟各种极端故障场景，而无需担心价值不菲的硬件受损。当你通过仿真迭代出一个表现良好的控制器后，那份代码在绝大多数情况下，只需要修改一行网络配置，就能驱动真实的Go2迈出第一步。这种“仿真到实物”的流畅体验，正是现代机器人开发的核心范式。
