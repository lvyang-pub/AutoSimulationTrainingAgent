# 评测报告：Go2 仿真训练自动调参智能体

> 本文档对应 Lab B 的**进阶要求**：构建可复现的测试任务与评测指标，并完成
> ≥1 轮「评测 → 分析 → 优化 → 再评测」的闭环。所有实验均以固定种子运行，
> 结果可复现（同一配置 + 同一种子 → 逐比特一致的回报，已验证）。

---

## 1. 评测目标与任务定义

**被测对象**：`TuningAgent`（ReAct + Tool Use + Memory + Reflection 的调参智能体），
底座 `deepseek-flash`。

**任务**：`go2_tune_v1` —— 让 Unitree Go2 在 MuJoCo 中学会以 1.0 m/s 前进。
Agent 只能通过提出超参配置、运行训练、读取指标、推理下一步来改进结果；
不能改代码。

**判分口径（客观、与 Agent 自评解耦）**：
- 奖励函数 **固定**（任务给定，Agent 对其的任何修改都被工具层忽略）；
- 单轮训练步数预算 **固定**（Agent 请求更大步数会被钳制，故"训得更久"不是可用策略）；
- 成功条件：`mean_return >= 190`（确定性评估，seed 固定）。

这两条"护栏"保证 Agent 与基线在**同一把尺子**下比较：回报跨轮次可比，
单轮算力一致。

**基线设计**：
- `naive`：从弱初始配置出发，跑**一次**默认超参训练，不做任何调整（下界）。
- `random`：与 Agent 相同的**试错预算**（6 轮），但随机采样配置、不做推理、
  不读结果、不反思（"无智能"对照）。

**单轮训练的算力现实**：CPU-only 环境，单轮 20k steps ≈ 90–150 s。
真实 Go2 步态 RL 需 ~1e9 steps，本地仅 ~1e5；因此在固定奖励、固定预算下，
本任务本质上是一道**超参优化**题，评测的是 Agent 的**搜索/推理效率**，
而非能否从零学出完美步态。这一取舍已写入需求文档 §1。

**评估指标**（对应任务要求的五类）：
| 维度 | 指标 |
|---|---|
| 任务成功率 | 达标任务数 / 总任务数 |
| 结果质量 | 最优 mean_return、速度跟踪误差、摔倒率 |
| 工具使用效率 | 工具调用次数、工具成功率（无异常比例） |
| 执行效率 | wall-clock 秒、总 token |
| 鲁棒性 | 注入工具故障后是否恢复 |

## 2. 第一轮评测（Round 1）

命令：
```
python scripts/run_eval.py --tasks go2_tune_v1 --methods naive random agent \
    --out eval/round1 --longterm memory/longterm.json
```

### 2.1 结果

| method | 结果 | return | lin_vel_err | fall_rate | trials | tool_calls | tool_errs | wall_s | tokens |
|---|---|---|---|---|---|---|---|---|---|
| naive | **fail** | 147.7 | 0.976 | 0.0 | 1 | 0 | 0 | 92.0 | 0 |
| random | **fail** | 34.2 | 0.224 | 1.0 | 6 | 0 | 0 | 1376.8 | 0 |
| agent | **PASS** | 200.6 | 0.996 | 0.0 | 6 | 7 | 0 | 800.0 | 46636 |

**结论**：只有 Agent 达标。
- naive 停在 147.7 —— 弱初始配置下"不调参"确实不达标，验证了任务有难度。
- random 6 个随机配置**全部摔倒**（best 34.2，fall_rate 1.0）—— 随机搜索在
  这个参数空间几乎必踩"发散崖"（高学习率 / 过软 PD 增益），反向证明了**推理
  的价值**：Agent 依靠诊断启发式避开了这些坑。
- agent 从 147.7 出发，通过推理性地抬高 `kp 30→80`、`action_scale 0.3→0.4`
  等，达到 200.6，且全程 **7 次工具调用零错误、全部走原生 function calling**。

### 2.2 第一轮暴露的问题（分析）

逐轮轨迹检查发现两处**效率缺陷**：

1. **达标后不停手**。Agent 在第 **2** 轮 trial 就已达到 200.6（远超阈值 190），
   但仍把 6 轮预算**全部烧掉**，多跑了 4 轮无意义训练。Harness 缺乏一个
   "目标已达"的显式信号。
2. **反思产出不可执行**。每一轮 reflection 都给出同一条建议——"把 timesteps
   提到 200000，训得更久"。但本任务**步数预算是固定的**，这条建议根本不可执行，
   白白消耗了反思的 token 与上下文。

这两点都不影响成功率，但**显著拉低执行效率**（800 s、46.6k token 中很大一部分
是冗余的）。这正是"评测 → 分析"要抓的东西。

---

## 3. 优化（Analyze → Optimize）

针对上述两点，做了三处**最小改动**（不改任务定义、不动判分口径，只让 Harness
与提示更"聪明"）：

| # | 改动 | 位置 | 目的 |
|---|---|---|---|
| O1 | **达标早停信号**：某轮 trial 达标后，在其 observation 末尾追加客观提示 `[objective check] the goal is now MET ... call finish now` | `src/agent/agent.py` run() | 让 Agent 知道"已达线"，无更优改动就收手 |
| O2 | **反思约束**：在 REFLECTION_PROMPT 中明令"奖励固定、步数预算固定、禁止建议'训得更久'"，并要求只推荐真正可调的参数（PPO / PD 增益等） | `src/agent/prompts.py` | 把反思从"不可执行的空话"变成"可执行的下一步" |
| O3 | **步数预算钳制**：工具层把 `timesteps` 上限钳到任务预算 | `src/agent/tools.py` | 保证基线与 Agent 单轮算力一致（同时堵死"靠训更久取胜"） |

配套新增单元测试（见测试报告）：达标信号确实注入 observation（`test_agent_loop.py`
+2）、奖励钉死与步数钳制（`test_tools.py` +4）。

> 注：O3 是**公平性**护栏，本身也是第一轮就应具备的；第一轮的分析把它与本轮的
> 效率优化一并落实。

## 4. 第二轮评测（Round 2，再评测）

命令：
```
python scripts/run_eval.py --tasks go2_tune_v1 --methods agent \
    --out eval/round2_agent --longterm memory/longterm_round2.json \
    --title "Round 2 - optimized agent"
```

### 4.1 结果

| method | 结果 | return | lin_vel_err | fall_rate | trials | tool_calls | tool_errs | wall_s | tokens |
|---|---|---|---|---|---|---|---|---|---|
| agent (R2) | **PASS** | 198.4 | 0.999 | 0.0 | **2** | **3** | 0 | **135.8** | **16638** |

逐轮轨迹：`trial_001` 弱起点 147.7 → `trial_002` 抬 `kp 30→80`、`action_scale
0.3→0.4` 得 **198.4（达标）** → 收到达标信号 → **立即 finish**。

### 4.2 与第一轮对比

| 指标 | Round 1 | Round 2 | 变化 |
|---|---|---|---|
| 成功 | ✅ | ✅ | 保持 |
| best_return | 200.6 | 198.4 | −1.1%（仍远超阈值 190） |
| 训练轮数 | 6 | **2** | **−67%** |
| 工具调用 | 7 | **3** | **−57%** |
| wall-clock | 800 s | **135.8 s** | **−83%** |
| 总 token | 46636 | **16638** | **−64%** |

**结论**：优化在**保持成功**的前提下，把执行成本降低到约 **1/5**。
早停信号（O1）直接带来轮数 6→2；反思约束（O2）省掉冗余 token；步数钳制（O3）
保证了比较公平。这验证了"评测→分析→优化→再评测"闭环有效：
**一轮分析定位到的效率缺陷，经由针对性改动，在再评测中被量化地消除，且未伤及成功率**。

## 5. 综合对照（基线与两轮 Agent）

| method | 成功 | best_return | trials | tool_calls | wall_s | tokens |
|---|---|---|---|---|---|---|
| naive | ✗ | 147.7 | 1 | 0 | 92.0 | 0 |
| random | ✗ | 34.2 | 6 | 0 | 1376.8 | 0 |
| agent R1 | ✓ | 200.6 | 6 | 7 | 800.0 | 46636 |
| agent R2 | ✓ | 198.4 | 2 | 3 | 135.8 | 16638 |

- **成功率**：Agent 1.0，基线 0.0。Agent 相对 naive 提升回报 ~34%，
  相对 random search 提升约 6 倍。
- **效率**：优化后的 Agent 用 **2 轮 / 136 s** 就达标，比 random 的 6 轮
  / 1377 s 快约 **10 倍**，同时结果好得多——效率与质量**同时**占优。
- **工具可靠性**：Agent 全程 0 工具错误、100% 原生 function calling（无 JSON
  回退），体现 Harness 的错误即观测（error-as-observation）契约有效。

## 6. 鲁棒性评测

`TuningAgent` 支持 `fault_after` 注入：令某一次 `run_training` 返回
`status=error`（模拟一次瞬时工具故障），观察 Agent 能否把错误当成 observation、
推理后重试。单元测试 `test_agent_survives_injected_fault` 覆盖了该路径：
Agent 观察到 `injected_fault` → 重新发起训练 → 正常继续，且故障轮**不消耗**
试错预算（在 dispatch 前注入）。

> 说明：本报告中的主评测未开启故障注入（`fault_injected=false`），以保证
> 基线/Agent 对比的纯净；鲁棒性通过单元测试独立验证。

## 7. 复现方式

```bash
# 基线（naive + random）
python scripts/run_eval.py --tasks go2_tune_v1 --methods naive random \
    --out eval/round1

# Agent（第一轮 = 优化前 / 第二轮 = 优化后）
python scripts/run_eval.py --tasks go2_tune_v1 --methods agent --out eval/round1_agent
python scripts/run_eval.py --tasks go2_tune_v1 --methods agent --out eval/round2_agent \
    --title "Round 2 - optimized agent"
```

产物：每个 `--out` 目录下含 `outcomes.json`（结构化指标）与 `report.md`
（本报告各表）；逐轮配置/指标在 `<out>/<task>/<method>/trial_*/` 下。
固定种子保证重跑一致。

## 8. 小结

| 评测结论 | 证据 |
|---|---|
| 智能体的推理带来实质增益 | Agent 达标，naive / random 均失败 |
| 优化能同时改善效率与保持质量 | R1→R2：轮数 −67%、耗时 −83%、token −64%，成功率不变 |
| 工具层契约稳健 | 0 工具错误、100% 原生调用、故障注入可恢复 |
| 评测可复现 | 固定种子；同配置逐比特一致（已验证） |

剩余局限与后续方向：
1. 三个任务（`v1`/`hard`/`tight`）目前只完整跑了 `v1`；`hard`（阈值 192）与
   `tight`（阈值 195 且要求低摔倒率）可作为扩展的多任务评测。
2. 反思目前是单轮诊断；可升级为"多轮自我批判"或引入独立 Critic 智能体做
   Multi-Agent 对照实验。
3. 长期记忆跨会话复用的效果尚未单独度量（可作为下一轮评测的变量）。
